# L2：安装 Skill 前后有什么变化

## 摘要

<ReportCard
  level="L2"

  summary="固定参考中，两侧十五个案例全部通过，因此没有观察到改善。"

## 先说结论：没有改善

固定参考使用十五个 develop 案例做 fresh 配对：

- baseline：十五个案例全部通过。
- Skill v0：十五个案例全部通过。
- 改善：零个。
- 退化：零个。
- 持平：十五个。

这不是一个“Skill 提升效果”的案例。固定运行让两侧使用相同的确定性行为，所以课程如实记录持平，没有为了教学效果制造翻转。

## 为什么这份结果仍然有价值

它验证了评测协议，而不是 Skill 质量：

- 两侧使用同一批任务和独立 fresh 环境。
- baseline 不安装 Skill，有 Skill 一侧安装通过静态检查的完整内容。
- 每个配对都能返回各自的 Trace、状态变化和判分证据。
- 报告会区分改善、退化、共同通过和共同失败。

这正是可信实验应该表现出的克制：没有观察到差异，就写“没有改善”。

## 触发检查说明了什么

固定参考还包含十条应触发请求和十条不应触发请求。在这组固定观察中，二十条判断全部符合预期。

它只证明触发评测链路可以工作。它不能替代更多自然表达下的实际测量，也不能证明完成任务的质量提高。

## 当前边界

Creator seed 和 develop packet 的独立人工复核仍未完成。因此，这份摘要不能升级为真实运行结论，也不能用于宣称 Skill v0 已经改善 Agent。

## 下一步怎样得到有意义的变化

1. 使用能暴露当前 Skill 缺口的 develop 案例。
2. 保持两侧任务、环境和评测协议一致。
3. 从失败证据生成候选，不要根据逐题留出反馈调参。
4. 同时检查改善与退化，不只报告总通过率。
